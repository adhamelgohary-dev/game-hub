# Extensibility

The module host composes built-in modules from one registration list. A feature can add a module folder or adapter, declare its routes and settings, and register its dependencies at composition. It receives read repositories and typed events, and calls service ports for work. Features with persistent state own an ordered migration in their namespace. This keeps existing library, session and Memory behavior independent of later modules.

| Roadmap item | Where it plugs in | Existing contracts it keeps |
| --- | --- | --- |
| v2 replay buffer, last 30–40 seconds | Add a Replay module with an optional stream port beside `WgcCapture.capture_once`. A Windows stream adapter reuses the foreground lease checks, yields bounded frames off the UI thread, and ends the stream on lost focus or session close. An encoder adapter handles FFmpeg with optional NVENC. Alternate OBS integration qualifies only if it can verify the target and prevent desktop capture. Replay owns retention, a configurable video budget and a `replay_clips` table keyed by session ID. | Game tracking still publishes the same session events. Periodic screenshots keep the same one-frame contract and schema. Replay owns continuous capture, encoding, and video lifecycle. |
| v2 Google Drive backup | Add an explicitly enabled Backup module. It asks storage for a SQLite-consistent snapshot and an inventory of referenced managed media. A snapshot lease protects referenced files from pruning until their bytes are staged into an immutable local copy. A pre-existing missing file fails the snapshot visibly and releases the lease. Test a simultaneous prune while bytes are staging. Package the verified relative paths and hashes in a versioned manifest. A Drive transport owns authentication, secure credential storage, resumable uploads and remote retention. Restore validates into a separate local root before switching via the store-location boundary. | Repositories and file references remain local and relative. The backup transport has no launcher, capture, session or Memory UI changes. Existing app modules never depend on a transport. |
| v3 local voice transcription | Add a Transcription module behind a local engine port. Subscribe to committed voice-note `MemoryChanged` events and scan for missing work on startup. The module resolves audio through `MediaRead` and keeps `note_transcripts(note_id, audio_digest, engine_version, language, text, status)`. Process in a bounded worker with a faster-whisper adapter and optional GPU acceleration. The digest and engine version let it resume or re-index safely. | Existing note payloads and Ogg files remain readable. Recorder, player and session state need no transcription dependency. |
| v3 search inside notes | Add a game-scoped search action and a Search read port. Index committed text note changes and completed transcripts into a rebuildable projection keyed by note ID and game ID. A later schema can use FTS5 with a fallback text search if unavailable. A result links to the existing game and session views. | Search does not change note authoring, voice playback, or timeline storage. Historical notes are indexed by reading them through a bounded repository query. |
| Module 2 Launch Doctor | Add `gamehub/modules/launch_doctor/` and register a per-game Diagnose action. The module reads capabilities and the last launch diagnostic, and correlates `LaunchRequested`, `LaunchFinished` and `GameStarted` by attempt ID. Its own read-only platform probes check install integrity signals, available runtime components and launch outcomes. Store any retained diagnostic reports by game ID in its namespace. | Library keeps ownership of discovery and launcher dispatch. Sessions still come only from the watcher, and Memory remains an independent event subscriber. |
| Module 3 Mods and Arabic Translations | Add `gamehub/modules/mods/` and register per-game install, uninstall and list views. Read the install location from `LibraryRead` and check active-session state before any modification. The module owns archive validation, verified destinations, patch manifests, backups, a rollback journal, and separate storage keyed by game ID. | The library continues to expose install info without managing patches. Session tracking, media and the UI language catalogs remain independent of translation packages. |

## Extension points

| Point | How new work enters |
| --- | --- |
| Library sources | Implement a `GameDetector` adapter and register the source with library composition. New persisted source values receive an additive schema migration when needed. |
| Platform services | Supply a Windows adapter or test double behind the process, window, capture, launch, audio or hotkey contract. New capture modes keep the foreground gate and receive their own purpose and budget. |
| Event subscribers | Subscribe to typed events without assuming delivery across application restarts. Reconcile durable work using repository queries and stable IDs. |
| UI | Register a game action, per-game view or settings panel. A feature owns its translations and uses the host's direction and localization settings. |
| Storage | Add feature tables linked by stable game, session or note IDs. Keep reversible derived data such as indexes separate from the original source records. Add a versioned media inventory or file format when a new feature needs one. |
| Settings | Add a validated namespace with defaults and an optional settings panel. The overall settings service continues to own persisted values and change notifications. |

The v1 build registers only Memory. Replay, backup, transcription, search, launch diagnostics and patch management add no operational services or dependencies to v1. There is no injection-based overlay extension.
