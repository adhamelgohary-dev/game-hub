# Game Hub working rules

- Follow PROMPT.md and STRUCTURE.txt. On resume, pull the verified private remote without rewriting history, then read HANDOFF.md, PROGRESS.md, DECISIONS.md and the design index. Run the full existing test suite and build first; fix any baseline failure with small, safe steps before starting new work. Follow the exact next step.
- Route work to the build roles in the design plan (simulate roles one at a time with labeled outputs if sub-agents cannot be spawned). Design comes before implementation. Update the relevant design file and DECISIONS.md before changing the design in code.
- Respect previous work: follow `docs/design/` and existing patterns; do not rewrite, refactor, rename, restructure, or delete existing code unless the current task requires it (and record why in DECISIONS.md). Note anomalies under Open questions in HANDOFF.md with the smallest safe fix.
- Use the four Review Council roles (Advocate, Critic, Neutral Analyst, Judge) on the overall plan and at each milestone gate. Record the Judge's verdict in docs/reviews and address required changes within two re-review rounds.
- Keep progress and handoff current after each task, including exact next step, in-progress work, fragile spots, open questions, and `Last worked on by: <model/tool>, <date>`. Write a Tutor entry per milestone. Tag every upcoming task `[simple]` or `[complex]`; smaller models defer `[complex]` tasks and note that in HANDOFF.md. Keep going across tasks and milestones with a brief 3–5 line status after each milestone, stopping only for owner tasks, irreversible decisions, completion, or tool limits. Preserve green main and push unfinished work on a `wip/<task>` branch when stopping early.
- Check tests and the staged diff before small commits. Keep the repository PRIVATE until the v1.1 Part E public-readiness audit is verified clean (after which the owner approved switching to PUBLIC); confirm repository visibility before pushing and after changes, and never force-push.
- Versioning and releases (v1.1+): use Semantic Versioning for GitHub Releases (`v1.1.0`, `v1.1.1`, `v1.2.0`; pre-releases `v1.1.0-rc.1`, `v1.1.0-rc.2`). Milestone tags (`m9`, `m10`, …) stay as plain git tags for internal tracking only; GitHub Releases use version tags only. Release title is `"GameRewind vX.Y.Z"` (previously `"Game Hub vX.Y.Z"` prior to the v1.2.0-rc.2 rename), notes come from `CHANGELOG.md` (`Added`, `Changed`, `Fixed`, `Security`), and attached assets are `GameRewind-Setup-vX.Y.Z.exe`, `GameRewind-Portable-vX.Y.Z.zip`, and `SHA256SUMS.txt`.
- The owner never runs commands: agents perform all builds, packaging (`.exe` / `.zip`), git operations, tags, and GitHub Releases (with assets attached) at every milestone. Publish a pre-release `-rc.N` for owner testing and publish the final release only after the owner says `"verified"`. Owner verification steps must be numbered clicks only, never terminal commands. Reply to the owner in short Egyptian Arabic while keeping all files, code, and technical docs in English.
- Keep v1.x offline and user data out of Git. Nothing runs in the background (no system tray, no "start with Windows" / `Run` registry entry, no background services or scheduled tasks); closing the main window exits the process completely. Use Windows Graphics Capture for the exact foreground game window (with `draw_border=False` where Windows allows it). Never inject, hook, read memory of, or open handles with write or debug rights to any game process; use only public Windows APIs and log nothing about other processes beyond the game's name and ID. Default protected/anti-cheat games to Strict mode (or automatic exit on external launch). Keep all files, code, and technical docs in English and the UI accessible in English and Arabic (with RTL). Never ask the owner to relay messages between agents or share passwords/tokens in chat.
